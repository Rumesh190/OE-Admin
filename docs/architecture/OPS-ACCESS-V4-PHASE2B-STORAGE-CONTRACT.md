### Important verified limitations

1. S05 commit linearization for cooperating synchronous callers is effectively journal removal; no durable transaction ID distinguishes committed success from an interrupted prepared attempt. Original-only journal is insufficient for notification replay or forward recovery.
2. Only S01/S03/S04/Audit journal-aware paths overlay originals. Actions, entitlements, generic relationships, tombstones and direct asset reads do not honor that journal. Events are attributable browser records, not immutable security logs.
3. Whole-array stores and cached readers can overwrite unrelated concurrent changes. S11 Web Locks cover participating creation only; revisions/locks do not currently protect all admin/lifecycle mutations.
4. Per-client record sequences can produce equal new business IDs in different clients, while some canonical lookups, routes and `OpsRecordRef` use ID alone. Reusing an explicit IQ sequence is not sufficient. A global uniqueness/composite-reference decision is required before multi-client D10; preserve existing IDs/links.
5. New client creation is immediately Active and does not atomically set an all-off map/staging barrier. Current fallback entitlements and old readers prevent promising no temporary IQ access without foundational integration.

## 3. Proposed technical contract: storage strategy

| Strategy | Benefit | Risk/trade-off | Recommendation |
| --- | --- | --- | --- |
| Extend current S04 version-1 object with all v4 collections | One familiar metadata root and existing cloning | Old readers ignore unknown fields and do not enforce new semantics; bumping version breaks current reader; global array contention/quota/history growth; unknown-field preservation varies across writers | Reject as first persisted v4 format |
| Add separately versioned v4 collections/envelope per client, managed by the **same canonical administration coordinator** | Separates schema/policy generation, avoids old readers treating v4 roles as legacy grants; client-contained validation/history; old keys untouched | Still coordinated with global v3 arrays; requires journal/read floor and staged activation; not a tenant security boundary | **Recommended**, subject to approval C01–C09 in gates |
| Move all data to a new backend/database immediately | Real server transactional/security foundation can be designed | Separate migration program; not a shortcut during isolated v4 frontend work | Deferred production phase; no backend assumed |

Use one logical `V4ClientAdministration(clientId)` envelope containing Departments, Champion/ZL/DL/DM assignments, FA-work verifier designations, assignment lifecycle events, command receipts, source-link uniqueness reservations, asset/delivery intents and activation metadata. These logical names allocate no physical keys. Final binding/partitioning/quotas require C01 approval. Do not copy people, clients, factories, Zones, Actions or Audits into it. Canonical CMs/FMs/FAs/grants remain S04; reviewed v4 policy references them.

Work capacity, verifier-selection snapshots and replacement history belong additively to the **canonical Action**, with sidecar IDs as references where needed. No second Action table in v4 metadata. Append assignment events to their originating lifecycle; do not duplicate full business/evidence payloads in generic events. Escalation requests/history are a future schema capability, absent/disabled until independently designed and reliable server notification delivery exists.

Old v3 Zone allocations and new explicit ZL records remain separate facts under explicit policy versions. Do not synthesize v3 grants or overwrite `leaderId`/allocations from a v4 assignment. Current Auditor eligibility still needs its approved v3 FM/grant/leadership policy; an integration adapter must be reviewed before new role records participate. New role presence alone grants nothing.

## 4. Proposed versioned envelope and readers

Documentation-only shape; names/versions below are proposed rather than emitted payloads:

```ts
interface ProposedV4Envelope {
  schema: { major: 1; minor: number; requiredCapabilities: readonly string[] };
  policyVersion: "ops-access-v4";
  organizationId: CanonicalClientId;
  collectionRevision: PositiveSafeInteger;
  committedTransactionId: TransactionId;
  activation: { state: "staged" | "active" | "suspended"; revision: PositiveSafeInteger };
  collections: {
    departments: readonly VersionedDepartment[];
    zoneChampions: readonly VersionedAssignment[];
    zoneLeaders: readonly VersionedAssignment[];
    departmentLeaders: readonly VersionedAssignment[];
    departmentMembers: readonly VersionedAssignment[];
    verifierDesignations: readonly VersionedActionSpecificDesignation[];
    assignmentEvents: readonly RetainedEvent[];
    operationReceipts: readonly ScopedReceipt[];
    sourceReservations: readonly AuditQuestionReservation[];
    assetIntents: readonly AssetPublicationIntent[];
    deliveryIntents: readonly DeliveryIntent[];
  };
  extensions?: Readonly<Record<string, unknown>>;
}
```

Every new row requires canonical ID/parent scope, positive safe-integer entity revision, originating policy version or an unambiguous inherited envelope policy, actual creation/update actor/time, and retained lifecycle events as applicable. Assignment lifecycle keeps original assignment/revocation attribution; reappointment is a new ID. Parent Zone is immutable. Event/receipt/intent rows have their own stable IDs; events append, receipts/intents have explicit monotonic processing revisions. All nested scope must equal envelope client and resolve to exactly one canonical parent. No display-name or ABC defaults.

**Read outcomes:** `available`, `not-initialized`, `recovery-required`, `unsupported-version`, `invalid-payload`, `scope-unavailable`. A read is side-effect free. Missing physical data returns not-initialized, not an empty operational client or seeded replacement. No first-read write. Known historical optional missing arrays may be projected as [] only according to an explicit version decoder; mark projection/upgrade required, preserve bytes and do not persist through an old writer. Missing required collections in a declared schema is invalid. Empty collections become durable only in an authorized initializer transaction.

**Version rules:** major/policy/required-capability unknown → deny protected new reads/writes, preserve raw bytes, surface upgrade/recovery guidance. A newer minor is writable only if every required capability is recognized and the exact known adapter proves lossless round-trip. Preserve unknown optional root/row/nested extensions; do not drop or interpret them as authority. If this cannot be proven, provide at most explicitly approved diagnostic reads and block writes. Additive upgrade is pure decode/preview first, then separately approved revision-checked transaction; never automatic destructive migration. A malformed existing value is never reset to defaults.

**Backward compatibility:** S01–S14 keys/payload formats remain unchanged for historical records. New v4 sidecars have separate dispatch; old readers must never consume their bytes as v3 state. New canonical Action/Audit rows require an explicit new-policy discriminator and complete scope; absent discriminator on old rows means legacy path, not new-v4 access. A partial discriminator/scope is invalid, never fallback. Before new v4 rows enter old canonical arrays, every reachable list/detail/mutation/report/evidence/relationship/deletion reader and writer must recognize and deny unsupported policy. Old tabs/bundles do not magically obey this: controlled compatibility floor and restart/quiescence gate are mandatory; production requires server rejection of old clients.

### Phase 2A discrepancies requiring later approved changes

- Department/assignment revisions/history references are optional today; persisted writable v4 rows need mandatory revisions and event/transaction association.
- Models have no schema/policy envelope, strict unknown-JSON decoder, idempotency/recovery/activation/intent data or lossless extension contract. TypeScript readonly is not runtime input validation or immutable storage.
- `IndependentVerifierDesignation` has attribution but cannot establish verifier qualification; selection stores opaque coordinator/verifier references, not actual authorized grants. R01–R03 remain gates.
- Some current evidence/review attribution retains display-name snapshots (for example Action upload `uploadedBy`), not a guaranteed canonical author ID. New-v4 evidence needs explicit actual-author ID/scope/transaction metadata; never infer missing historical author IDs from names.
- Existing `MyAction` lacks required Client/Factory/policy/capacity/selection fields; adding work snapshots to a sidecar instead would create conflicting Action truth. Future canonical additive adapter is required.
- Phase 1A validates supplied current facts. Phase 2A historical identity helpers intentionally retain inactive references and do not perform runtime read authorization, deactivation dependency scans or storage upgrades.

No model or validator is edited by this document.

## 5. Proposed authorization and write validation sequence

1. Resolve actual authenticated person internally; caller actor ID/context token is an expected match only. Separate platform/client administrative modes from factory operations.
2. Validate explicit person-bound active Client/Factory context/revision and target scope. Refresh retains the selection but every protected operation revalidates; no implicit first/ABC fallback.
3. Reject existing v3 or v4 pending recovery/unsupported formats; acquire approved locks and load coherent validated current state, not cached form copies.
4. Validate active Client → Factory → Zone → Department chain; canonical people/memberships/FA/base roles/grants/explicit assignments as required. Historical-read adapters do not qualify inactive targets for new work.
5. Enforce operation-specific actual-actor authority: SA attachment, same-client CA FA appointment/Action-specific designation, FA ZL/Champion/DL management and eligible same-Zone DL/FA member allocation. Data presence is not authority; unresolved qualifications return `POLICY_UNRESOLVED`.
6. Check read-set/entity/collection/auth-context revisions and opaque before-image tokens; revalidate unique-active tuples, one led Zone, same-Zone Department allocations and ZL alignment against the proposed resulting graph.
7. For Action work, validate immutable origin/eligible owner and captured capacity, mandatory creator/completer independence, independently authorized coordinator and selected verifier before submission. Draft creation may lack verifier; FA designation is Action-specific, not CA verification power.
8. Run complete R08 dependency checks for deactivation/revocation/reassignment. Unknown module dependency coverage blocks the operation, not an empty-work assumption.
9. Build allowlisted internal write plan/events/receipt/intents; validate quota/serialized content and recovery availability. Re-resolve actor/context and all authorization dependencies immediately before publication, including after async asset preparation.
10. Commit under section 7 protocol; no success notification/read publication before commit. Context/revision/grant change aborts, never silently chooses another owner/verifier.

No client-provided eligibility booleans, role names or generic JSON patches may bypass this sequence. Production performs it server-side within the authoritative transaction.

## 6. Proposed revision/concurrency contract

**New v4:** entity revision starts at 1; expected `Absent` is explicit for create, never inferred from a missing historical revision. Update/lifecycle/selection revision increments exactly once on successful business mutation. Client envelope collection revision increments once per committed transaction. Use a scope/assignment-graph revision (or the envelope revision initially) to detect competing tuple insertions and R08 phantoms; per-entity checks alone do not prevent write skew. Append events include before/after revisions. Never decrement/reuse committed revision; recovery restoring an uncommitted attempt restores its original revision, not a new business change. Overflow rejects.

**V3 shared keys:** no retrospective revision-field injection. Read-set token records exact raw-byte digest/absence for whole S01/S03/S04/Audit/Action/entitlement/relationship/tombstone payloads being consulted or changed. Preserve before bytes/unknown metadata. Whole-key digest detects unrelated changes conservatively; context/actor/grant dependencies also need reread tokens. This is compare-before-write, not localStorage CAS. Sidecar revisions cannot serialize concurrent old code writing a global legacy array.

**Cooperating browser demo:** require Web Locks; no write fallback to a localStorage “lock flag,” lease timeout or timestamp. Existing S11 lock is useful but insufficient. Proposed universal acquisition order is existing business-record-creation lock **then** new logical administration-coordinator lock when both are needed; admin-only operations take the latter and never acquire the business lock inside it. Adapt all relevant writers/recovery to the same order before activation. Do not nest `withBusinessRecordCreation` again when already holding its lock. Registered-store refresh/fixture initializers must not run as an unauthorized side effect in new v4 preparation.

Under locks, reread coherent current bytes, compare every expected token/revision, recompute eligibility/cardinality/dependencies, commit synchronously without awaiting unrelated work, then notify. Prepare expensive Blobs outside lock with explicit intents, and revalidate after await. Lock support/compatibility floor missing → reject new-v4 writes. Cross-tab messages/storage events only invalidate UI caches; they do not authorize/reconcile a write.

**Limits:** cooperating same-origin updated tabs can serialize local work; nonparticipating/older tabs, browser-owner edits, extensions, separate browsers/devices, process/device failure and separate backend users cannot be excluded securely by this design. A check followed by set without universal cooperation can lose updates. If the compatibility floor cannot be established, new-v4 live writes stay disabled. Production needs server transactions/row constraints/atomic expected-version updates and authorization in that same boundary.

| Scenario | Required future behavior |
| --- | --- |
| Two FAs add different leaders | First commits graph/envelope revision; second detects stale graph, reloads and explicitly retries valid intent; no silent whole-array merge |
| Two tabs lead same person in different Zones | Serialize and validate entire factory/person graph; second conflicts even with different assignment IDs |
| Department inactivated during dialog | Parent/status/dependency revision mismatch; no assignment or success event |
| ZL revoked before pending write | Current authority/graph mismatch, reject; no replay of stale eligible fact |
| Verifier replaced before submission | Expected selection/Action revision mismatch; preserve revisions/evidence and require fresh independent selection validation |
| Client/Factory context switches | Person/context revision mismatch, cancel stale save/upload publication |
| Cached admin tab | Reload current bytes under lock; conflict response retains form intent only, no automatic privilege-sensitive retry |
| Pending journal | Freeze protected writes and coherent reads; operator recovery, not another commit |

**Idempotency:** scope receipts by actual actor + canonical client/factory + operation + key, with semantic input digest, transaction ID, committed IDs/revisions and outcome. Same successful request returns the same currently authorized result without increment/event duplication; different digest returns conflict. Check current authentication/read permission before receipt projection. Pending attempt returns recovery-required. Aborted recovered attempt may be retried explicitly with a new attempt ID, never resurrecting rolled-back success. No blind retry of changed owner, reviewer, grant, context or dependency decisions.

**ID reservations:** S11 high-water reservations are permanent, including aborted creations. Journal the reservation intent before touching the counter; treat the counter as monotonic/non-rollback, not a value to restore. Preserve gaps and tombstone reservations. Production needs global uniqueness. Proposed preferred compatibility option is globally unique new business IDs preserving existing IDs/formats through a reviewed cross-tenant reservation strategy; alternatively fully scoped composite routes/refs require a larger migration. Final choice C05 is unresolved: no IQ/D10 generation until proven safe across old ID-only readers.

## 7. Proposed coordinated transaction and publication contract

Separate logical v4 journal, not a new shape written into S05. Physical key binding/version requires approval. Existing S05 preimage array and recovery allowlist stay unchanged until separately reviewed integration. Proposed future readers check both journals and a reader/writer compatibility floor; old S05 recovery must not be invoked on a v4-owned attempt. Mixed/ambiguous ownership is quarantined. Do not claim current old readers obey new barriers.

Journal fields: schema/version, transaction ID, phase/revision, actual actor/context/scope, operation/idempotency/semantic digest, read-set versions, before and proposed after byte images/digests of allowlisted targets, committed receipt/event IDs, permanent ID-reservation intents, staged asset IDs and delivery intents. No evidence binary, arbitrary caller key list or secret credentials. Journal is private diagnostic/recovery data, not an operational read bypass.

**Phases and commit point:**

1. Under required locks and fresh validation, persist/verify `Prepared` journal **before** target writes or permanent reservation writes. No journal → no protected writes.
2. Apply monotonic ID reservations, then planned versioned sidecar/canonical metadata targets in deterministic allowlisted order; all upgraded readers project before images while Prepared. Events/receipts/intents are part of these after images, not published separately as success.
3. Verify target bytes/revisions and asset durability, then atomically replace the journal value with **Committed** containing verified target digests. This single-item marker is the proposed cooperating-reader business commit point, not a cross-store hardware durability guarantee.
4. Readers now project verified after state; success result may be acknowledged with the committed receipt. Finalize target verification and journal cleanup under the same locks; do not start another metadata writer or modify delivery-intent status while the Committed journal still pins after-image digests.
5. After coherent targets and terminal receipt plus durable pending asset/delivery intents exist, remove the journal idempotently, release locks, then notify subscribers and let delivery/cleanup workers process intents in subsequent revision-checked transactions. A retained Committed journal is a completion/replay task, not a reason to roll business state back. It temporarily blocks new metadata writes until finalized, without undoing committed success.

Prepared crash/failure → restore original allowlisted bytes/absence, quarantine or safely remove only new unreferenced staged assets, retain monotonic counters, no success event/delivery. Committed crash → forward-complete verified after state and intents, never undo acknowledged business state. Any target not equal to expected before/after bytes, malformed journal, missing committed after image or conflicting writer → quarantine/manual review; never overwrite an unknown newer value. Repeated recovery requires the same locks/checks and durable progress; no clearing storage. Delivery retries are at least once unless the transport supports stronger idempotency; unique intent/recipient inbox keys prevent duplicate app-inbox events, not a universal exactly-once external delivery promise. Backend performs these logical effects in real transactions/outbox rather than emulating a distributed transaction in localStorage.

## 8. Evidence, relationships and D10

**Binary/metadata protocol:** prepare a durable scoped asset intent in its own short, authorized coordinated transaction before the Blob; this is staging metadata, not published business evidence. It can identify an existing record or canonical Audit/question source plus a new asset reservation, without fabricating an Action. Release locks before binary work; every staging/main transaction separately follows Prepared/Committed. No binary in journal. Store Blob in IDB, wait for transaction completion, verify availability/checksum. Revalidate actual actor/context/owner/record revisions before metadata commit. Main expected tokens must incorporate the known committed staging receipt while retaining the user decision/entity/auth read-set; any unrelated change still conflicts. This is not permission for an automatic general stale-write rebase (C04/C06). Metadata references a staged asset only through the coordinated plan; until Committed it is not published operationally. Existing digest-shared assets are references, not owned new uploads: never delete on rollback without complete reference proof. Cleanup failure leaves a recoverable intent/quarantine; it must not hide the metadata failure or delete a historical/shared file. IDB cannot join a localStorage transaction. Storage eviction/device loss cannot be solved by hashes or journals; server-backed protected files and recoverable storage are required for production.

**D10 domain key:** `(clientId, factoryId, auditId, canonical questionId, sourceModule=audit)`; creator/owner display names and titles are not identity. Validate unchanged canonical question and source scope. Under locks check active and reserved/tombstoned links plus idempotency. First committed request owns one source reservation and canonical Action; concurrent different key/actor cannot produce a second Action. Identical authorized retry returns existing authorized result; changed intent conflicts. Deleted/broken required link is reserved/unresolved pending explicit repair policy; no new task or compliant finding fabricated.

Store actual authorized executor/creator IDs, immutable source/owner origin, exact captured work-role assignment reference and evidence authors. Verifier may be absent in creation/draft; independently authorized coordinator selects before review submission; CA designation only for the specific FA Action and grants no CA verification. Submission checks canonical person/history, current selection and context revisions; replacement preserves old selection/submission evidence. No new Action status or Audit review stage.

Current S07 create + S06 link + optional S09 relationship are separate publication boundaries. Calling those helpers sequentially inside a try/catch does not become atomic. `rollbackCreatedAction` cannot retract an already delivered notification and may itself fail. The future canonical service must expose an internal prepared mutation/commit path under one coordinator, then publish. Do not construct another Action store. Derived S09 edges can remain derived; if a saved edge is essential, its write is a transaction participant or a committed idempotent rebuild intent, never contradictory independent authority.

Audit finding required-link checks remain mandatory. Audit completion stays independent of whether every linked Action is closed (`tests/audit-independent-action-closure.test.ts`). Audit execution still follows v3 grants/own-Zone/FA direct execution/signatures/scoring; narrow U06-A permits only Audit-origin task/detail/evidence/review operations under exact actor scope, with general Actions/manual/unrelated sources disabled. The current ABC/legacy creation adapter and missing canonical Action scope make D10 an explicit later gate.

## 11. Proposed API contract — documentation only

Proposed CommitResult distinguishes `rejected`/`aborted` (no committed business mutation), `committed` (receipt), `committed-recovery-pending` (business committed, finalization pending) and `outcome-unknown` (must inspect/recover). A cleanup/notification failure after Committed cannot be returned as an ordinary pre-commit rejection. Recovery of committed state preserves the actual historical author even if that person has since lost authority; retry projection still requires current read permission.

The following signatures are conceptual, not created public APIs or HTTP routes. ActorRef is an opaque expected-session/context reference that every operation resolves internally; it cannot contain trusted caller roles. ExpectedSet includes entity, envelope, graph/auth/context revisions and exact legacy read-set tokens. Result errors include `UNAUTHENTICATED`, `CONTEXT_INVALID`, `FORBIDDEN_OR_UNAVAILABLE`, `INVALID_PAYLOAD`, `UNSUPPORTED_VERSION`, `NOT_INITIALIZED`, `STALE_REVISION`, `DUPLICATE_ASSIGNMENT`, `INDEPENDENCE_CONFLICT`, `VERIFIER_REQUIRED`, `DEPENDENCIES_INCOMPLETE`, `POLICY_UNRESOLVED`, `RECOVERY_REQUIRED`, `QUOTA_OR_STORAGE_FAILURE`, `IDEMPOTENCY_CONFLICT`, `ID_COLLISION`, `CONCURRENCY_UNAVAILABLE`. Pre-commit failure publishes no success event; committed-but-response-lost is recovered through receipt, not a new mutation.

## 12. Production security boundary and completion

Browser-local checks/locks/JSON/IDB can demonstrate a cooperating single-browser policy and recovery protocol. They cannot securely authenticate people, prevent local record tampering, enforce tenant row/file access, serialize different devices, protect immutable logs or guarantee background SLA notification delivery. Production requires authenticated server identity, server-authoritative context and policy, tenant-scoped API/query/file enforcement, transactional constraints/expected-version updates, durable events/idempotency/outbox and reliable scheduler. No real backend is inferred from client code or AI routes.

The task ends at these three design documents. Source/data/workflow/key/schema/runtime behavior is unchanged. No application tests/browser UAT or production readiness is claimed.
