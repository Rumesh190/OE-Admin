# OPS Access v4 Phase 2B — Failure, Recovery and Publication Matrix

Date: 22 October 2026. **Proposed technical contract, documentation only.** No recovery utility, new journal, storage key, migration, test fixture or runtime change was implemented.

Read with the [storage contract](OPS-ACCESS-V4-PHASE2B-STORAGE-CONTRACT.md) and [implementation gates](OPS-ACCESS-V4-PHASE2B-IMPLEMENTATION-GATES.md). Source inventory S01–S14 and approval gates C01–C09 are defined there. Existing behavior, desired behavior and unsupported guarantees are deliberately separate.

## 1. Existing and verified recovery boundary

`features/five-s/administration/access-v3-store.ts::commit` writes original `{key,value}` entries to `ops-access-v3-pending-transaction-v1`, writes selected directory/configuration/Audit payloads and v3 metadata/events sequentially, then removes the journal before notifying. Failure restores original bytes; failed rollback retains a pending journal. `lib/administration-storage.ts::readAdministrationPayload` exposes originals for participating keys while pending. `recoverAdministrationTransaction` requires actual platform SA and restores only its four allowlisted payloads before clearing the journal.

This protects selected v3 writes, not all stores. The existing journal has no transaction ID, after images, committed phase, revision set, receipt, asset intent or delivery outbox. Current Actions, relationships, entitlements, tombstones, IndexedDB Blobs and some direct readers do not participate. A current recovery operator cannot safely recover proposed v4 targets by passing them to the existing recovery function. Its allowlist must not be loosened to arbitrary supplied keys.

Existing single-key `safeSetStorage` failures preserve old value and selected callers roll memory back. Some generic paths have weaker failure semantics (for example relationship removal ignores persistence result); these are source findings, not fixes in this task. Evidence Blob writes commit separately from canonical metadata. Existing high-water ID reservations are intentionally permanent. A failed creation can consume an ID without publishing a record.

Existing tests inspected: `tests/access-v3-phase1.test.ts` (invalid payload/pending journal/original-read behavior), `tests/access-v3-phase2.test.ts` (one-write failure, interrupted rollback, reassignment/history), `tests/action-evidence-quota.test.ts`, `tests/audit-evidence-quota.test.ts`, `tests/ux-relationship-write-failure.test.ts`, `tests/module-record-ids-and-order.test.ts`, deletion and Action workflow suites. Their earlier reported passes are historical; no application tests were executed for these documents.

## 2. Proposed transaction states and invariants

Logical journal state is `Prepared` or `Committed`, with transaction ID and monotonic journal revision. Optional recovery progress markers do not create a third business commit point. Physical storage binding/retention is C01/C04; nothing is allocated here.

- **Before Prepared:** no protected entity/event/link/asset/ID-reservation write. Pure validation and read-only previews may fail freely.
- **Prepared:** original images remain the visible coherent state for all upgraded readers; writes are frozen except the transaction/recovery owner under the same approved locks. After images, revision read-set, receipts/events, staged asset/delivery intent IDs and permanent reservation intents are retained in the journal. Do not publish success.
- **Commit point:** after all planned metadata and required Blobs are verified, a single journal-item replacement marks Committed. This is only a logical publication point for cooperating upgraded browser clients, not server transaction durability or a guarantee against storage loss.
- **Committed:** after state and business events/receipt are authoritative. Lost acknowledgment triggers receipt replay, not duplicate mutation. Recovery forward-completes after images/intents and finalizes journal; it does not undo committed business state. Metadata writers and delivery-status updates wait until journal finalization so they cannot invalidate pinned after-image digests.
- **Quarantined diagnosis:** malformed/unsupported journal, unknown writer bytes, missing verified committed assets/after images or ambiguous ownership blocks writes and operational projections. Preserve raw bytes; do not guess whether success happened.

Ordinary rollback restores exact preimages/absence, preserving unknown fields and committed revision numbers. Never roll back permanent business-ID high-water reservations or reuse tombstoned/consumed IDs. Safe recovery recognizes already-restored targets and is repeatable; it never executes domain authorization commands again from scratch, transfers work, changes signatures or fabricates a new business actor.

## 5. Idempotent recovery algorithm proposal

1. Actual authorized recovery actor resolves canonical platform technical authority; no factory operational grant follows. Acquire the same lock ordering as business writers, reject other journal ownership and freeze impacted operational writes.
2. Validate journal schema/version, allowlisted targets, scope, image digests, transaction/journal revisions, event/receipt consistency and monotonic reservation intents. Keep unknown bytes and diagnostics if unsupported. Do not interpret arbitrary key names from caller-controlled input.
3. If Prepared, restore only targets equal to known original/proposed images or already-recorded recovery steps. Preserve original absence exactly; restore old committed business revisions, do not restore monotonic counters. Do not run the business command anew or emit business-success notifications.
4. If Committed, verify/reapply exact known after images and receipt, verify retained pending asset/delivery intents, and finalize the journal before any worker updates intent state. Subsequent asset/delivery state changes use separate revision-checked transactions, not in-place edits of the journal-pinned envelope. Do not select a new actor/verifier, alter dates, or append another creation/assignment event.
5. Record attributed recovery progress/outcome separately from original business actors/events. If recording recovery progress fails, keep sufficient journal images to repeat; no double business effects. Recovery itself is revision/idempotency-checked.
6. Clear journal only after consistent target images, terminal command outcome and durable pending cleanup/delivery intents exist. Cleanup/delivery may continue from retained intents after journal removal; a pending intent must not be lost with the only journal copy.

All steps are proposals, not capabilities of the existing S05 implementation. New journal/collection storage layout, retained receipts, byte budgeting, progress event placement and operator authorization are approval gates C01–C04/C07. Repeated-crash fixtures must prove termination/idempotency or explicit safe quarantine, not rely on a unit test with only one thrown write.

## 6. Evidence-specific failure policy

Do not put Blob content in localStorage/journal. Record transaction-owned staging intent in a separately committed short staging transaction before storing a new Blob, with immutable tenant/record-or-Audit-question/author/category references and content digest. Release locks for binary work, then validate main-transaction expected tokens against that staging receipt and unchanged entity/authority decisions; do not silently rebase unrelated changes. A digest is an integrity/dedup hint, not ownership or authorization. Existing shared/hash-derived assets may be referenced from several old Action submission revisions or Audits; a simple “new metadata failed, delete key” rule is unsafe for those keys.

Commit metadata only after required asset availability and authorization recheck. Failed metadata requires a durable orphan/retry record. Garbage collection requires complete registered references across canonical records, submission revisions/history, tombstones/deleted retained records and active intents. R08/reference coverage incomplete → retain/quarantine Blob, no hard delete. Browser eviction or an already-missing historical asset is reported unavailable with original metadata retained; no fabricated bytes/signature/evidence proof. Production needs a server object lifecycle/upload session with protected read URLs and transaction/outbox references, not direct tenantless key access.

## 7. Operator experience proposal

Show a restricted, scoped “Recovery required” state with transaction ID, stage, affected logical stores, detected time and non-sensitive cause. Disable protected mutation controls and detail projections that could reveal incoherent after state. Offer only validated platform Recovery/diagnostic export paths; do not recommend clearing localStorage, deleting IDB, changing role flags or resaving fixture data. Preserve unsupported/corrupt payloads for reviewed restoration.

Status distinctions: business not committed; business committed but response lost; business committed with pending notification/cleanup; unknown/quarantined. These are transaction/diagnostic states, **not new Action/Audit statuses**. Technical recovery actor/time is separate from source creator, signer, reviewer or assignee.

No current UI is modified. Availability of recovery diagnostics must not expose another tenant's people, task title, evidence or journal bytes to ordinary users. Secure production recovery requires independent server authority and protected audit logs.

## 8. Explicit limitations and verification plan

A journal can coordinate visibility only for code that consults it. No design here secures localStorage against browser owners or prevents older/noncooperating tabs from writing direct keys. `navigator.locks` in existing record creation is verified, but does not cover current administration/events/evidence/entitlements. Compare-before-write cannot replace database CAS/unique constraints. A Blob transaction cannot atomically commit localStorage. A browser outbox cannot guarantee delivery after the app closes. Reliable operational escalation SLA notifications require server-side delivery before activation, per the Phase 2B brief.

Future verification: pure envelope/state/revision/recovery simulations first; inject failure before/after **every** write, marker, Blob callback and cleanup; then controlled storage integration on isolated test adapters; then actual authorization/tenant context; targeted legacy regression; one consolidated automated browser acceptance after approved integration. Include unknown versions/extensions, null-vs-missing targets, equal-name foreign IDs, revoked roles, stale tabs, shared assets and permanent sequence gaps. No browser UAT or failure-injection test was run during this documentation-only task.
