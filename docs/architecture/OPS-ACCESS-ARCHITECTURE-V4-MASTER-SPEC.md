## 2. Approved hierarchy and invariants

Metric Mind platform → independent Clients → Factories → Zones → independent Departments → explicitly assigned Department Leaders/Members. Zone Leaders remain between factory oversight and Department leadership. Zone Champions are separate factory-wide oversight assignments, not membership in every Zone.

| Relationship | Enforced invariant for new v4 assignments |
| --- | --- |
| Client → Factory → Zone → Department | Exactly one canonical parent per child; validate the entire active parent chain; no Department transfer between Zones |
| Factory → Champions | Multiple active people allowed; each Champion reads authorized progress across all factory Zones; no automatic mutation/admin permission |
| Zone → Leaders | Multiple active people allowed; at most one active led Zone per person per factory |
| Department → Leaders/Members | Multiple leaders and members; one person may have several Department assignments only within one Zone per factory |
| Person → roles | Multiple roles via separate explicit assignments; no inferred membership, grant, verifier or module permission |
| Cross-Zone work | Department operational membership across different Zones in one factory is forbidden. Champion oversight and authorized cross-Zone Audit execution are not Department membership |
| Historical facts | Stable IDs and captured actor/scope/evidence history survive revocation, reassignment and inactivity |

Approved U02: a Zone Leader's Department Leader/Member assignments must remain within the Zone they lead. Department Leader and Member assignments together obey the single operational Zone per person/factory invariant. A new-v4 Zone Leader cannot retain new-v4 Department assignments in another Zone. Existing v3 multi-Zone allocations remain readable and authoritative for approved Audit rules; they must not be auto-converted or normalized to satisfy v4 cardinality. New v4 assignment commands must refuse conflicting changes pending explicit resolution.

## 3. Canonical model contracts

### 3.1 Common conventions — proposed

Reuse canonical person IDs and existing `organizationId`, `plantId`, `zoneId`; do not invent another tenant/directory/Action database. New entity IDs follow the existing prefix + UUID allocator after validation. Proposed prefixes and storage payload/version are technical decisions, not allocated records.

For each new entity retain `id`, explicit scope IDs, `status`, `createdBy/createdAt`, `updatedBy/updatedAt`, revision and lifecycle event references. Assignment records additionally retain `assignedBy/assignedAt`, `revokedBy/revokedAt/reason` when ended. Existing v3 field names remain compatible; do not require invented fields on old payloads. Events capture actual actor ID, target ID, policy version, context, before/after, reason and correlation ID. Display names are historical snapshots, never authorization keys.

Active/inactive structures and Active/Revoked assignment proposals are distinct from existing Action statuses. Ended assignments are retained, not hard-deleted or reused as unrelated identities. Reappointment should create a new lifecycle ID. Require one active assignment for each unique person/role/scope tuple; multiple different people are permitted. Parent IDs are immutable. Deactivation/revocation re-evaluates current authority and unfinished work; never silently transfers ownership.

New-v4 reads begin with actual active person + authorized Client/Factory context and canonical target ownership, then record/module policy. Historical retention does not mean access for everyone or former members. Approved U08 retained-read rule for new v4 workflows: a currently authorized actor may inspect retained history in scope; a former member receives no new access merely from a past assignment. U08 approves this current-authorization rule for new v4 workflows. Explicit legacy v3 retained-read paths stay unchanged until a separately reviewed transition.

### 3.3 Transactions and recovery

Current administration commits journal original directory/configuration/metadata (and scoped Audit reassignment payloads), roll back failures and expose originals while recovery is pending. `lib/administration-storage.ts` and `access-v3-store.ts` are the reuse points. Pending recovery blocks protected writes; do not reset data or hide corruption.

Proposed v4 changes must validate the entire resulting assignment graph, payload allowlist and expected revision before IDs/files/events/notifications are published; recheck actual actor immediately before commit. A batch covering person/CM/FM/role changes is atomic or fully rolled back. Preserve unknown compatible payload fields, existing storage keys and original records. New collection/version readers and recovery allowlists need explicit design and tests before migration approval. Browser localStorage has no true multi-tab transaction: add proposed revision/conflict detection and fail/reload on stale updates; do not claim database isolation.

D10 source-link + Action creation and escalation state + event + notification delivery intent need separately reviewed transaction boundaries. An IndexedDB binary written before metadata failure must be tracked for rollback/recovery without deleting referenced historical assets. After recovery, notification intents must not duplicate or announce rolled-back records. A future backend uses server transactions, scope enforcement, durable events and an outbox; no backend is implemented here.

## 4. Authorization contract and tenant context

Proposed effective permission order:

1. Resolve authenticated actual person, not caller-provided role/name; expected actor ID only detects stale/forged UI context.
2. Resolve explicit active Client/Factory context against canonical memberships and assignments. Platform and client administration contexts are separate; SA and CA do not need or receive implicit FM to administer their approved scope.
3. Validate unique active ownership chain, entitlement/capability, explicit assignment and operation-specific permission. Ambiguous IDs, missing context, stale revisions or pending recovery fail closed.
4. Check Department/Zone scope and person-level segregation; no combined-role bypass.
5. Validate lifecycle/evidence/assignment preconditions, then commit attributed changes and authorized notifications.

Proposed `ActiveAccessContext`: authenticated person ID, context mode (platform/client/factory), canonical organization/factory IDs where appropriate and context revision. The session context is a selection of existing authority, never a grant. No fallback to ABC or the first eligible factory for a new v4 operation. Deep links validate canonical target against selected context; if switching is required, show an explicit authorized switch, never silently expose foreign content. Context-switch and sign-out must invalidate cached records, reports, linked titles, exports, evidence previews and open mutation dialogs; Back/Forward revalidates access. Approved U01 persists the explicit Client/Factory selection across refresh, bound to the authenticated canonical person. Every protected read/write revalidates it; persisted context is not authority. Missing, revoked, inactive or foreign selection becomes unavailable with no fallback. Context persistence is independent of listing tabs, which still reset to All under existing listing rules.

Proposed reviewed cross-client attachment command: actual platform SA, explicit target canonical person/client, identity confirmation and reason, active person/client, global uniqueness checks, no duplicate active CM, expected revision, no automatic CA/FM/FA/Zone/Department/grant/entitlement. Preserve existing memberships; inactive CM requires explicit reactivation review, not a fresh duplicate. The actual-SA attachment grantor and exact identity-confirmation/approval procedure remain proposed R10; U01 alone does not approve attachment. A restricted platform identity-review UI must avoid exposing foreign-directory search to CA/FA. Creation of another person with the same display name is allowed only for a confirmed distinct human, not to bypass attachment guards.

Read filtering must be shared by list/detail/search/counts, Action Center, dashboard, report/export, relation previews and evidence downloads. Authorized aggregate access is not permission to read every attachment or personal profile. Champion views use an oversight projection, and other authorized leaders viewing an escalation do not automatically get its underlying record/evidence. Server authentication, row/file enforcement, tenant queries and protected audit logs are separate production gates; local demo identity switching cannot establish those guarantees.

## 8. Champion escalation proposal

Approved routing is Department Leader → Zone Leader → Factory Admin. Champion chooses one eligible accountable person per level; other authorized leaders may read but cannot respond as that person. Candidate sets use canonical active explicit assignments in the request's Department/Zone/factory. If a request lacks a Department, do not invent one: R04 must specify whether DL level is pending or explicitly skipped. No recipient means pending authorized resolution, not automatic higher authority.

Proposed states (not approved names): `PendingRecipient`, `AwaitingAcknowledgment`, `Acknowledged`, `ResponseProvided`, `Rejected`, `Resolved`, `Cancelled`. “Overdue” is a derived SLA condition, not an Action status or automatic route transition. Routing level and response state are separate. Plan/reassignment requests describe requested outcomes and never execute underlying mutations.

| Event / command | Validation and effect |
| --- | --- |
| Raise/select | Actual active factory Champion; authorized source/progress scope; selected eligible accountable recipient at current level; retain initial selection and SLA snapshot |
| Acknowledge | Only current selected recipient; actual actor/context; attributed timestamp required before response processing |
| Reject | Selected recipient; nonempty reason; retain any acknowledgment and response history. Whether rejection can itself serve as acknowledgment is R04 |
| Respond/submit plan | Selected recipient; retain plan/text/evidence references with scoped read rules; does not change Action assignment/status |
| Same-level reroute | Champion explicitly selects another eligible recipient after rejection; append history and end old accountability, never erase response |
| Manual next-level escalation | Champion explicitly chooses one eligible next-level person; no automatic leap; preserve lower-level responses/recipient/SLA deadlines |
| SLA expiry | Deadline comparison appends/deduplicates overdue event and notifies Champion; no automatic next-level routing or underlying reassignment |
| FA overdue | Remains overdue with Champion notification; no CA/SA operational substitution |
| Resolve/cancel | Authority/evidence requirements R04; proposal Champion records resolution with reason after response, but never closes underlying operational records |

Approved U07 uses configurable **calendar-hour response SLA per escalation level**, configured only by an explicitly assigned Factory Admin in that factory. Expiry notifies the Champion and never progresses automatically. Exact duration values, clock start, acknowledgment treatment, timezone presentation and pause/reset/reroute rules remain R05; resolution/cancellation and remaining state semantics are R04. Snapshot it on each accountable recipient selection so later configuration changes do not rewrite history. Recipient loss/deactivation stops their future response writes and requires explicit reroute; retain prior events. Cross-Zone routing cannot assign Department membership.

Notifications are required business behavior but delivery architecture is not yet approved. Existing `lib/notifications/notification-store.ts` provides browser-local immediate notifications/deduplication, not a durable scheduler or reliable background SLA delivery. Propose minimal authorized recipient/Champion delivery intents with idempotency keys; in-browser timer/re-evaluation can only demonstrate expiry while the app is running. Reliable background scheduling, retry and notification transport are a separate dependency; do not expand the postponed Notification Center silently. No new engine or existing VM escalation modification occurs in this task.

Existing VM escalation is board/meeting/topic based, with Open/Acknowledged/In Progress/Resolved/Returned statuses and optional Action link. It is not this Department hierarchy request. Preserve VM logic/IDs/history; shared transport reuse requires later explicit adapter approval, not status/model conflation.

## 9. Department lifecycle and allocation

Department Active/Inactive is independent of its parent Zone's legacy `department` string. New Departments are explicit records, not automatic conversions of “Production.” Require approved lists; do not copy ABC Departments/Zones into IQ by name.

Proposed deactivation command scans canonical Actions (including pending review/rework), module work that explicitly references the Department, unresolved escalation accountability/requests and active allocations. Referenced history blocks hard deletion. Any unfinished work blocks deactivation until completed or explicitly reassigned through its authorized domain command with reason/history. The completeness of this dependency index is an acceptance gate: integrating a new module must register its checks before Department mutation becomes available for it.

Allocation removal and person inactivity must likewise check unfinished owned/review/allocation obligations; do not silently transfer them. Unfinished work may be reassigned only to currently eligible scope/role recipients, preserving origin Department/owner history and evidence. If no replacement exists, block deactivation. Inactive Department disallows new allocation/work and mutation; currently authorized retained-history reads remain available with inactive labels. Parent inactivity removes effective operational authority but never cascades deletes. Explicit reactivation revalidates parent chain and allocations; no expired/revoked grant is resurrected implicitly. Recovery restores the whole consistent pre-change graph, not a partially inactive Department.

## 12. Phase 1 reconciled authorization contracts — proposed interfaces

The business decisions in the Phase 1 brief are approved. The following exact interface shapes, error codes, persistence layout and command names are **proposed technical contracts**, not TypeScript implementations or implementation approval. A pending R-series policy must return a blocked result rather than infer authority. Existing v3 function signatures/errors remain unchanged until a reviewed adapter is authorized.

### 12.1 Shared request/result and failure contract

Every proposed protected command takes: explicit context identifier/revision; expected canonical actor ID (comparison only); canonical target IDs; operation-specific allowlisted fields; expected entity/assignment revisions; nonempty reason where reassignment, revocation or designation is involved; and idempotency/correlation key for writes. Actual actor comes from authenticated session resolution; callers cannot supply effective roles, grants, verifier eligibility, timestamps or history.

Success returns: authorized minimal target projection, canonical IDs, current revision, context revision, operation/correlation ID and attributed committed event ID for writes. Candidate/policy queries return eligible IDs/projections and non-sensitive blocked-reason codes, not unfiltered directory records. A denied read returns no target content; UI uses an unavailable/forbidden state. All results are subject to current read authorization even on idempotent retry.

Proposed failures: `UNAUTHENTICATED`, `CONTEXT_REQUIRED`, `CONTEXT_INVALID`, `ACTOR_MISMATCH`, `FORBIDDEN_OR_UNAVAILABLE`, `INVALID_INPUT`, `INACTIVE_SCOPE`, `CARDINALITY_CONFLICT`, `STALE_REVISION`, `INDEPENDENCE_CONFLICT`, `VERIFIER_REQUIRED`, `UNFINISHED_DEPENDENCIES`, `POLICY_UNRESOLVED`, `RECOVERY_REQUIRED`, `PERSISTENCE_FAILED`. Foreign/missing private records share `FORBIDDEN_OR_UNAVAILABLE`; detailed conflicts are returned only inside already authorized scope. Failures publish no entity/link/asset reference/notification/success event. No auto-reset or fallback. Persistence failure returns failure plus recovery reference when applicable, never a success-shaped result. New errors are proposed, not facts about current commands.

### 12.2 ActiveAccessContext

- **Inputs:** select/restore request `{mode: platform|client|factory, organizationId?, plantId?, expectedActorId, expectedContextRevision?}`. IDs required for the chosen mode; irrelevant IDs rejected. Restored preference is keyed/bound to authenticated person and contains selection IDs/version only, never authority booleans.
- **Output:** validated context `{contextId, personId, mode, organizationId?, plantId?, revision, authorizationRevision}` plus minimal labels/available capabilities. Restore after refresh re-resolves person, active canonical ownership, CM/FA/FM/explicit role authority and entitlements for the requested operation. Administrative access is resolved by its own assignment; SA/CA is never converted into factory operator.
- **Rules:** persist approved Client/Factory selection on refresh; revalidate on every protected read/write/evidence/export/retry. Context selection does not grant membership. Switching person cannot carry another person's context. Invalid persisted selection yields unavailable context; no ABC/first-factory substitution or silent deep-link switch. Explicit authorized user switch is required to change context. Every mutation checks the target ownership against context and invalidates stale dialog/upload publication.
- **Boundary/errors:** missing/invalid/stale/forged selection returns context/actor/conflict errors before data projection. A client-mode CA may designate for one Action in an explicitly addressed factory of that client; this is client administration, not operational factory-context authority. Refresh persistence does not persist listing tabs.

### 12.3 Department and independent role commands

- **Department input:** create `{organizationId,plantId,zoneId,name,code,expectedParentRevision}`; metadata update `{departmentId,name?,code?,expectedRevision}` under approved uniqueness/locked-field adapter; status change `{departmentId,status: Active|Inactive,reason,expectedRevision}`. Proposed nonempty trimmed name/code unique case-insensitively per Zone. Parent IDs cannot be edited or transferred.
- **Assignment input:** `{personId,role,organizationId,plantId,zoneId?,departmentId?,expectedGraphRevision,reason}` with separate role-specific command allowlists; revocation uses `{assignmentId,expectedRevision,reason}`. Zone Champion has factory scope only, ZL has one Zone, DL/DM has exact Department chain. No role-array/person-permission payload accepted.
- **Authority:** U10 actual assigned FA appoints/revokes Champions, ZLs and DLs. FA or eligible DL allocates/removes Department Members only within authorized same-Zone scope; proposed conservative DL bound is its own active Departments, pending any approved extension R07. No DL creates accounts, factory/Zone roles, CA/FA assignments or grants.
- **Validation:** active canonical person/CM/FM and parents as applicable, unique active person-role-scope tuple; many leaders allowed per Zone/Department; one led Zone/person/factory; all Department assignments in one operational Zone/person/factory; a ZL's Department assignments must be in its led Zone. Legacy multi-Zone authority cannot be collapsed or used as a hidden v4 membership (R06).
- **Output/error:** canonical Department/assignment ID, scope/status/revision/event; no implicit grants or account creation. Unknown foreign scope denied, cross-Zone/duplicate/conflicting leader assignment returns authorized cardinality conflict, unfinished work blocks revocation/deactivation (R08). Historical references retained; inactive reads require current authorization. No hard deletion of referenced Departments.

### 12.4 Work capacity determination

- **Input:** Action assignment/reassignment request `{actionId or canonical source reference, responsiblePersonId, workCapacity: DepartmentMember|DepartmentLeader|ZoneLeader|FactoryAdmin, capacityAssignmentId, originScope, expectedActionRevision}`. Capacity is explicitly supplied for validation by an authorized assigning actor, not guessed from highest/global role. Multi-capacity selection and eligible assigning actor details remain R02.
- **Validation:** resolve the cited active assignment and immutable source/client/factory/Zone/Department; for new Department-level Actions, owner remains within originating Zone at creation and every reassignment (U03). Zone Leader's Department assignment follows its led Zone (U02). Capacity must match actual work and hierarchy; lowering the capacity solely to lower review requirements is denied. Existing general Action assignment policy does not automatically become a v4 assigning capability.
- **Output:** retained `{responsiblePersonId, workCapacityAtAssignment, capacityAssignmentId, originScope, assignmentActorId, assignedAt, assignmentRevision}` and applicable verifier tier. Reassignment appends previous/new actor/capacity/scope facts, never edits creator/completer history or moves origin. Wrong scope/capacity fails before mutation; ambiguous policy returns `POLICY_UNRESOLVED` (R02). No verifier is required for otherwise valid creation/draft work.

### 12.5 Independent verifier eligibility, selection and replacement

- **Eligibility input:** `{actionId,expectedActionRevision}` in authorized context; candidate query resolves actual role capacity at assignment, current hierarchy and immutable actor history. Output is deterministic unique eligible-ID list with assignment references; sorting never appoints anyone.
- **Mandatory filters:** current authorized active canonical person/scope; appropriate approved DM→DL, DL→ZL, ZL→FA tier; FA work needs current Action-specific designation. Verifier differs from creator and retained actual completer/submitting workers whose work is reviewed; no combined-role/reassignment bypass. Same display names do not imply identity. Additional participation exclusions/qualification details are R01/R03.
- **Selection input:** `{actionId,verifierPersonId,verifierAssignmentId or designationId,expectedActionRevision,reason}` from an independently authorized coordinator, neither creator nor completer. Output is retained selection event/ID, selected canonical person/authorization reference and new Action revision. Coordinator entitlement/grantor is R01; do not infer it from role or designate it by UI dropdown alone.
- **Submission:** creation and draft work may lack a verifier (approved U04). `submitActionForReview` must reject with `VERIFIER_REQUIRED`/`INDEPENDENCE_CONFLICT` if no currently eligible coordinator-selected verifier; no submission revision/review status/notification is published on failure. Revalidate the retained coordinator selection actor against creator/completer history as well as verifier eligibility at submission, review, rework and closure; a coordinator who has since completed the work cannot leave a valid self-selection path. Existing statuses and evidence/category/cost/completion requirements stay intact.
- **Replacement:** proposed `{actionId,previousSelectionId,newVerifierPersonId,authorizationReference,reason,expectedRevision}`; preserve old selection, submitted revision/evidence and prior review events. Exact replacement authority and whether/how selection changes a pending submitted review are R01; until approved this operation returns `POLICY_UNRESOLVED`, not automatic reassignment or self-selection.

### 12.6 Client Admin Action-specific verifier designation

- **Input:** `{organizationId,plantId,actionId,verifierPersonId,reason,expectedActionRevision,expectedDesignationRevision?}`; actual active CA of that client in client context. Canonical Action must be new-v4 FA-capacity work in that factory. Proposed revoke uses exact designation ID/revision/reason; no factory-wide wildcard designation.
- **Output:** retained Action-specific designation `{id,actionId,verifierPersonId,organizationId,plantId,status,designatedBy,designatedAt,revocation metadata,revision}` plus event. This permits candidacy for this one Action only; coordinator selection remains a separate authorized operation.
- **Boundary:** CA does not gain execution, verification, reviewer-selection coordinator authority, FA, Auditor grants or unrelated source/module rights. Designated person still passes current eligibility/independence each use. Creator/completer cannot designate themselves around independence; candidate eligibility, CA self-designation where independently qualified, and revocation during pending review remain R03/R01, blocked pending approval. CA authority alone never makes that CA an eligible verifier.

### 12.7 Champion escalation and SLA policy

- **Configuration input:** actual assigned FA supplies `{organizationId,plantId,responseHoursByLevel: {departmentLeader,zoneLeader,factoryAdmin},expectedPolicyRevision,reason}`; each level requires an explicit positive finite calendar-hour value (proposed validation, no invented defaults). Output is versioned policy/event with actual config actor/time. No Champion/CA/SA configuration override inferred.
- **Request input:** Champion `{sourceReference,organizationId,plantId,zoneId,departmentId?,requestType,reason,level,recipientPersonId?,expectedRevision}`. Validate actual Champion scope and source visibility. Initial routing is DL level; a higher-level recipient requires a retained authorized manual progression event, not a caller-supplied level shortcut. Candidate query returns authorized DL/Zone ZL/factory FA projections; one selected recipient is accountable. Missing candidate keeps request pending rather than inventing a person or auto-progressing. Department-less entry remains R04.
- **Response/routing:** selected recipient acknowledges; rejection requires reason; other readers cannot respond. Champion can explicitly select alternate eligible same-level recipient after rejection or manually escalate to next approved level. These commands return updated request/revision plus retained event; no Action assignment/status changes. Resolve/cancel and remaining transition details are blocked R04.
- **Expiry:** proposed UTC deadline arithmetic adds configured calendar hours, including nights/weekends; this implementation interpretation, clock start/reset/pause and notification transport/delivery guarantees remain R05. Snapshot policy/version per accountable recipient interval. Approved U07 requires Champion notification on expiry; no automatic route progression. Overdue FA stays overdue, no CA/SA substitution. Output of expiry handling is deduplicated overdue event + delivery-intent reference; intent is not proof of delivered notification. No local timer may be claimed reliable while browser is closed.

### 12.8 Cross-client existing-person attachment

- **Proposed input:** actual-SA-reviewed `{targetPersonId,targetOrganizationId,identityReviewReference,reason,expectedDirectoryRevision,expectedMembershipGraphRevision,idempotencyKey}` in platform context. Actual-SA grantor, evidence/consent rules and inactive-membership reactivation procedure await separately approved R10; they are not new authority from this document.
- **Validation/output:** unique active canonical person/client, target ID confirmed as same human; no duplicate or inactive CM shortcut; append one ordinary CM and attributed event. Return authorized CM projection and committed revision. Preserve all existing client/factory roles/history, and add no CA/FM/FA/Zone/Department/Auditor/verifier permission or subscription.
- **Failure:** foreign people remain unselectable by CA/FA; duplicate/inactive/ambiguous target or unresolved identity review blocks operation, not duplicate person creation. Idempotent success is returned only to an authorized retrier. No raw localStorage write or temporary role elevation.

## 13. D10 reconciled source-link and evidence contract

Approved U06-A is a narrow source-derived capability, not an entitlement alias. For new v4 records, require Audit entitlement in selected client plus active authorized canonical Audit/question context; reject arbitrary `sourceModule`, manual tasks, other sources, caller-supplied completed/review fields, foreign scopes and stale actor/context. Actual executor authorization remains Phase 2; no new Audit reviewer stage.

Canonical create/link inputs propose `{auditId,questionId,expectedAuditRevision,ownerAssignment,workCapacityAtAssignment,idempotencyKey}` with explicit authorized source/owner scope. Department-level work remains within Audit finding's originating Zone. Department eligibility/non-Department work route awaits R02; no fabricated Department/member/reviewer. Verifier may be absent at create/draft; coordinator selects eligible verifier before submission, with CA Action-specific designation for FA work where applicable. No automatic creator/auditor reviewer fallback for new v4 tasks.

**One Action per canonical Audit/question:** uniqueness key is `(organizationId, plantId, auditId, questionId)` plus canonical source-module identity. First authorized create publishes one canonical Action and matching question link. Same key and semantically identical request retries return the same authorized Action, not another ID/evidence copy. Same key with different owner/content or an existing different link returns conflict requiring explicit authorized edit/reassignment. Tombstoned/deleted or inconsistent links stay reserved and blocked pending reviewed repair/replacement policy R06; do not create a second task to hide missing required linkage. No title/name/legacy ID prefix inference for new links.

Proposed commit/recovery validates both revisions before allocation/publication, retains pre-transaction Action/Audit/relationship/asset references, publishes source link and Action metadata atomically, then emits success/delivery intents. Interrupted readers see coherent originals and writes stop pending recovery. Idempotency marker/reservation is part of the same transaction; notifications/retries cannot announce orphan tasks. Blob publication and rollback must not delete original/referenced evidence. Physical journal/IndexedDB concurrency and restart behavior require approved R06 design and tests before implementation; localStorage journaling alone is not a database transaction guarantee.

**Minimum task access:** scoped Audit task projection/detail only for its eligible owner, independently authorized coordinator, selected verifier, explicit Action-specific CA designation operation or other separately approved exact permission. Being an auditor, CA, Champion or source-record reader alone does not confer unrestricted task mutation/read; an Audit may show only its authorized link projection. Permit only the task's authorized work/evidence/submit/review/rework/close operations through canonical commands; no unrelated task enumeration, general Action Center, manual creation, other source access or extra module flags.

**Evidence:** resolve actual actor, validated active context, canonical Action/source scope, authorized operation, current owner/reviewer/selection and revision before binary upload or preview/export. Revalidate before reference publication after asynchronous upload. Capture Action ID, evidence category, canonical actual author/time and retained submission revisions; use authorized asset IDs/references rather than trusting a caller storage key. Denied/stale upload publishes no link or success event; cleanup tracks only unreferenced new assets. Legacy evidence/signatures and storage keys remain untouched. No browser-local file utility is a production file-authorization boundary.

**Lifecycle:** retain existing Action statuses, Type-at-start rules, submission revisions/evidence, rework and closure requirements. Required real Action linkage still gates noncompliant Audit finding completeness; no Action creation failure may be disguised as compliant. Audit completion does not require linked Action closure; Action review never becomes an independent Audit review stage.
